# 时间静止四段测试：第一轮用户反馈

日期：2026-10-08。证据来源是用户观看云端成片后的文字反馈；本轮没有取得或直接观看四个视频。模型文件、LoRA、步数及实际送入模型的提示词是否被改写仍待核对。

**结论：按用户反馈，四段均未完成预定的“暂停时间→拨箭→抱走地上的孩子→放稳孩子→恢复时间”情节，不能列为成功范例。** 第四段只有整体失败描述，不能为它补填具体病症。

前三段明确共同出现“初始已经抱人”和“箭提前落地”。第二、三段还分别报告多手和重复孩子。不可据此计算冻结失败、多手或穿模在全部四段中的发生率。

## 与原提示词核对

脚本核对四条原提示词，以下内容全部存在：女侠双手空着入场；同一个小男孩摔在街心；箭在空中停住；左掌持续抬起；右臂抱起该男孩；先放稳孩子、再放下左手；解除之后箭才落到空街面。原文件及四条 prompt 的哈希已存入 `反馈与核对.json`。

因此，“没有写明空手入场或先后关系”不是准确诊断。文字中写清了这些状态，出片没有遵守。此前 lint 的 0 ERROR / 0 WARN 只代表它所检查的格式与机械规则，不能证明剧情执行、人体、冻结或穿模通过。

## 目前可以确认的学习结果

1. 这份完整 15 秒一镜到底模板在用户本次云端结果中未跑通，不能因文字核对或盲写通过就称优化成功。
2. 原测试以删除全局活动表演段为唯一文本改动；本轮没有展示整体成功的版本，不能把删除该段视为足以解决这场戏的办法。缺少直接观看和逐项评分，也不能判定删除对冻结本身完全没有影响。
3. 初始状态、能力触发时机、箭的落定、抱人交互都同时出了问题。用这一场复杂救人戏作为首次冻结能力排查，失败后难以定位最先失效的环节。测试设计需要先减小任务范围。

## 待验证假设

- 过多状态转换集中在一段连续镜头里，当前配置未保持事件顺序。
- 后半段“抱着孩子移动”和“箭插在地上”的状态提前出现在开头；这与反馈吻合，但不能据此断言内部生成机制或具体是哪句话导致。
- 持续抬左手、右手拨细箭、右臂托抱同一冻结孩子、穿越箭阵与运镜一起增加了交互负担；它们与多手、重复孩子、穿模有关的因果尚未分离。
- 实际模型、加速 LoRA、采样设置、提示词改写或缓存也需核对；目前没有证据把问题归因于其中任何一项。

## 下一轮排查边界

优先做独立的短冻结测试：女侠空手入场，箭在飞，抬手后箭停在空中，保持至结束。先移除抱人、拨箭、穿越箭阵和解除恢复，明确标为诊断用例，不冒充原完整剧情的改写交付。

冻结基础动作可用后，再分别加拨箭、抱人和恢复，观察是哪一步引入错误；如果基础冻结也失败，先核对有效提示词与模型配置。原故事的一镜到底要求仍保留，不因本轮失败直接改成通用“必须切镜”，也不推广成“H3 做不了异能”。

本轮只保存反馈、核对原稿与形成排查假设，没有修改 skill 行为规则、替换原 JSON、调用付费 API 或提交新渲染任务。
