# Codex 执行方案：按出片问题优化 h3-power-fx

适用：`seed_expansion_v1` 这批 24 段（12 情节 × 种子 2026100801 / 2026100802）已经出片，用户发现有问题。目标是**一轮一轮把出问题的情节修好，只把两个种子都过关的写法升级成 skill 规则**。

做法照抄冻结飞箭那一轮（`RENDER_FEEDBACK_1` → `2` → `3`）：先记原话，追问到能定位，最小改动，同种子重跑，过关再写进 skill。

---

## 第一部分：用户先做

1. 打开 `tools/context_ir/powers/render/seed_expansion_v1/反馈表.csv`（Excel 或 WPS 都行），**每一行（每段视频）都填**：
   - `状态`：`通过` / `有问题` / `没看`
   - `实际视频文件名`
   - `画面问题原话`：看到什么就写什么，按时间先后写，例如"杯子没滑就直接飞起来，落下时变成两个杯子"
   - `声音问题原话`：没问题就空着
   - 没问题的段也要填`通过`。它们是这轮的对照，不会被改。
2. 保存，放回原位置（文件名不变）。
3. 把下面这句话发给 Codex：

   > 先运行 `git fetch origin claude/cloud-mode-status-19m8rv`，再运行 `git checkout origin/claude/cloud-mode-status-19m8rv -- tools/context_ir/powers/CODEX_RUNBOOK_POWERS_FIX.md`，然后严格按这个文件的第二部分执行。反馈表我已经填好。

每轮出片后重复第 1 步（填这一轮的反馈表），然后告诉 Codex"第 N 轮反馈填好了，继续"。

---

## 第二部分：给 Codex 的指令

### 硬规则

1. **分支**：继续在 `codex/h3-powers-skill-calibration` 上工作。不 rebase、不 force push、不建 PR、不合并到别的分支。
2. **不花钱**：不调用 MiniMax API，不提交任何生成任务。出片只由用户在本地或云端做。
3. **密钥**：不打印、不写入任何密钥，不运行打印全部环境变量的命令。
4. **可以改的文件**：
   - `tools/context_ir/powers/` 下的新文件（反馈记录、诊断、新一轮的提示词和 JSON）；
   - `h3-power-fx/` 下的文件（只在第 6 步，按升级条件改）；
   - `dist/h3-power-fx.skill`（第 6 步重新打包）。
   - **不改** `h3-shot-prompt/`、`h3-action-prompt-design/`、`h3-director-json-review/` 的规则和任何 `.py`。如果确实发现主 skill 的规则有问题，写进 `tools/context_ir/powers/analysis/MAIN_SKILL_PROPOSALS.md`，交给 Claude 审核。
5. **不动通过的段**：标了`通过`的情节，提示词一个字都不改。它们是对照，也是回归测试。
6. **一次只改一处**：每个失败情节每轮只改一个变量（一句描述、一个镜头安排、一个数量），其余文字、时长、种子和 JSON 字段保持一致。改了几处就是几个变量，必须如实写出来。
7. **证据不夸大**：
   - 用户没说的不算观察。`通过`只代表用户看过、没提问题。
   - 一个种子过、一个没过，记"不稳定"，不算过。
   - lint 通过不等于效果通过。
   - 不把 2 个种子写成"稳定成功率"。
8. **每步完成后提交**，提交信息写清这一步的结果，然后 `git push`。

### 第 1 步：收反馈

1. 读 `反馈表.csv`。如果所有行都还是`待生成`，或`有问题`的行没写原话，就停下，请用户按第一部分填好。
2. 把原表复制成 `tools/context_ir/powers/analysis/RENDER_FEEDBACK_4_user.csv`，不改用户的字。
3. 生成 `RENDER_FEEDBACK_4.md`，列一张表：情节 | 种子 1 | 种子 2 | 用户原话（逐字）。
4. **追问**：只问会改变修法的问题，一次最多 5 个，每个都能用一句话或一个选项回答。参照飞箭那次：
   - 问题从出现时就有，还是中途才变？
   - 是两个种子都这样，还是只有一个？
   - 多出来的东西（手、人、箭、杯子）是从哪里冒出来的？
   - 动作是提前、延后，还是顺序反了？

   用户回答后，原话追加进 `RENDER_FEEDBACK_4.md`。

### 第 2 步：诊断

每个`有问题`的情节写进 `analysis/DIAGNOSIS_4.md`，一个情节一节：

1. **现象**：用户原话（逐字），以及发生在第几镜、第几秒附近。
2. **提示词里对应的原句**：从 `seed_expansion_v1/提示词原文/<id>.txt` 原样摘出。
3. **归类**（只选一个主类）：

   | 类 | 意思 | 例子 |
   |---|---|---|
   | A 写漏 | 提示词没交代这件事 | 没写箭头朝哪边，结果反了 |
   | B 写了没做到 | 写清楚了，模型做不到或做不稳 | 写了"只有一个杯子"还是变成两个 |
   | C 设计太难 | 一个镜头里同时发生的事太多 | 抱孩子 + 走路 + 满天箭 + 人群静止 |
   | D 种子差异 | 只有一个种子出错，另一个正常 | 先不改提示词，记"不稳定" |
   | E 设置问题 | 采样、LoRA、时长和提示词对不上 | 让用户核对配置，不改提示词 |

4. **两个种子都错的排在最前面**。只有一个种子错的（D 类）这轮先不修，下轮观察。
5. **修法假设**：写一个最小改动，说明为什么它可能有效。按下面的"常见病症起手修法"挑第一个试，不要一次全上。

### 常见病症起手修法（都是假设，不是规则）

| 病症 | 先试的一处改动 |
|---|---|
| 效果提前发生（箭提前落地、杯子没等触发就动） | 触发前写明对象还处于什么状态（箭正在飞、杯子静止在桌上），再用 `As her palm reaches shoulder height, …` 把效果绑在触发动作上 |
| 方向反了（箭头、飞行方向、受力方向） | 写两端的形状和位置，以及和人物的远近（飞箭那次唯一验证过的修法） |
| 东西变多（手、人、武器、杯子） | 在数量变化的那一镜写清数量，同时减少这一镜里同时出现的同类物件 |
| 穿模（箭穿过人、手穿过物件） | 写清两者之间的空隙和距离，例如"一前臂远"；减少接触动作 |
| 一个镜头里事件太多、看不懂 | 改成两个镜头，或拆成两段；不要只靠加字 |
| 人走路发飘、不流畅 | 减少走路，改成站定或少走几步 |
| 特效形状、颜色、大小不对 | 写清颜色、形状、大小，以及它在身体哪个部位、离身体多远 |
| 特效没出现 | 先确认不是 E 类；再把特效从远景挪到近景，或单独给一个特写 |
| 一打多人数乱 | 每个切镜写剩几个人、在画面哪一侧；人数多的先减到能看清的数量 |
| 结束状态不对（光没灭、剑没回鞘） | 最后一镜单独写结束状态，并留至少 1.5 秒 |

**两轮最小改动后同一个病症仍然两个种子都出现**，就停止改字，改用绕开的设计，并在 `DIAGNOSIS` 里写明"H3 本地做不稳"：
- 拆段；
- 换景别，只拍结果；
- 用首帧图 I2VA；
- 把这件事挪到插入特写里。

### 第 3 步：出下一轮测试

1. 新建文件夹 `tools/context_ir/powers/render/fix_round_<N>/`，N 从 1 开始。
2. 只放**第 2 步定了修法的情节**，每个情节两段：同样两个种子 `2026100801` / `2026100802`、同样时长、同样 JSON 字段，只改第 2 步写的那一处。
3. 一轮最多 8 段，太多看不仔细。超出的情节排到下一轮。
4. 文件夹里放：
   - 导播台 JSON（结构照抄 `seed_expansion_v1` 的 JSON，`schemaVersion` 5，素材为空，latentRelay 关闭）；
   - `提示词原文/<id>.txt`；
   - `改动说明.md`：每个情节一行，写"原句 → 新句，改的是哪个变量，对应 DIAGNOSIS 哪一节"；
   - `反馈表.csv`：格式照抄 `seed_expansion_v1/反馈表.csv`，`重点核对`一栏写这次要看的那一件事。
5. 每个提示词运行 `python h3-shot-prompt/scripts/lint_prompt.py <文件> --seconds <秒数>`，整份 JSON 运行 `python h3-director-json-review/scripts/lint_json.py <JSON>`。ERROR 必须修掉；WARN 逐条核对，记进 `改动说明.md`。
6. 用 `diff` 确认新旧提示词只差改动说明里写的那几处，把 diff 结果存成 `检查记录.txt`。
7. 提交并推送，告诉用户：这轮几段、在哪个文件夹、每段重点看什么。然后**停下等用户出片**。

### 第 4 步：收这一轮的反馈

用户填好 `fix_round_<N>/反馈表.csv` 后，按第 1 步的方法记成 `RENDER_FEEDBACK_<4+N>.md`，并更新 `DIAGNOSIS`：
- **两个种子都过**：这个修法"本地出片过关"，进入第 6 步。
- **一个过一个不过**：记"不稳定"，可以再试一轮同一个修法的加强版，或换下一个修法。
- **都不过**：换常见病症表里的下一个修法，回到第 3 步；两轮都不行就按"做不稳"处理。

### 第 5 步：回归检查

每当有修法准备写进 skill，先想清楚它会不会影响**已经通过**的情节。会的话：

1. 把受影响的通过情节也按新规则改写一版，放进下一轮 `fix_round` 一起出片。
2. 两个种子仍然通过，才算回归没坏。

### 第 6 步：写进 skill

只有满足下面全部条件的修法，才写进 `h3-power-fx`：

1. 两个种子都过关；
2. 改动说明能说清是哪一处起作用（只改了一处）；
3. 回归检查没坏。

写法：
- 规则写进 `h3-power-fx/references/powers-and-effects.md` 对应能力的那一节。每条规则后面括号注明证据，例如`（本地出片过关：fix_round_1 都市念力，2 个种子，2026-10-xx）`。
- 新增 `h3-power-fx/references/troubleshooting.md`（异能病症 → 修法），只收出过片的病症；没验证过的修法标"待验证"。
- 两个种子都过的完整提示词，按 `rendered-freeze-arrow.md` 的格式收为参照，标明证据等级和没覆盖的情况。
- 证据等级只用这三级：`官方文本样本` / `本地出片过关` / `本地同种子对比胜出`。
- `h3-power-fx/SKILL.md` 只在入口和"参照与证据"里加指针，主体保持短。
- 重新打包：先删掉 `__pycache__`，再把 `h3-power-fx` 文件夹打包成 `dist/h3-power-fx.skill`（zip 格式）。
- 跑一遍 `validation`：所有链接能打开、所有引用的提示词原文和来源 JSON 逐字一致，结果写进 `analysis/VALIDATION.md`。

### 第 7 步：每轮收尾

在 `tools/context_ir/powers/PROGRESS.md` 更新一张总表：

| 情节 | 当前状态 | 轮次 | 用的修法 | 证据 |
|---|---|---|---|---|
| 都市念力 | 通过 / 修复中 / 做不稳 | … | … | … |

然后提交、推送，告诉用户：
- 哪些情节已经过了；
- 下一轮要出几段、看什么；
- 哪些情节判定为本地做不稳，改用了什么绕开的设计。

### 停下来问用户的情况

- 反馈表没填，或原话太笼统（"有问题""莫名其妙"），定位不到镜头和时间；
- 修法需要改剧情（删角色、删动作、改结局），先问用户能不能接受；
- 需要首帧图或参考图（I2VA / Ref2VA）；
- 发现主 skill（`h3-shot-prompt`）的规则和异能需求冲突；
- 怀疑是 E 类设置问题。
