# MiniMax H3 提示词调研报告（2026-10-07）

目的：弄清楚为什么别人的 H3 提示词能按想法出片，而本地按旧 skill 写的提示词出片很乱；据此重写 `h3-shot-prompt` skill。

> 说明：这份报告写于官方接口校准和本地出片对比之前。里面的镜头数、字数、每镜时长下限等数字已被后来的结果取代（`h3-shot-prompt/references/official-calibration.md`、`tools/context_ir/analysis/RENDER_RESULTS_1.md`、`RENDER_RESULTS_2.md`），以 skill 现行规则为准。

## 一、核心结论

### 1. 本地缺了官方流水线里最关键的一环

官方 H3 是三段：**H3-Context-IR → H3-Base → H3-Regenerate-2K**。开源的只有 H3-Base。官方 README 原话："H3-Context-IR is critical to the quality of the final output, so we strongly recommend incorporating it into your generation pipeline or following the Prompting Guidance to build your own context-processing system."

Context-IR 是一个闭源的多阶段改写系统：把用户随手写的需求（加上参考图、视频、音频）改写成一份固定文体的英文文档，再交给 H3-Base。官方的复现脚本里能看到改写后的原文（已收进 skill 的 `references/examples.md`）。

**这就是"别人写得好"的主要原因**：在海螺、fal、官方 API 上看到的高分提示词，大多是改写之前的原文，平台会先用 Context-IR 把它改写一遍。比如官方示例"竖屏家庭冲突"，原文只有三小段松散的描述；能出好片，是因为后面有 Context-IR。本地跑时，你写的文字原样进 H3-Base，没有任何改写。

开源社区也验证了这一点：open-h3-ir 的作者用同模型、同种子、同参考图对比，原样输入的视频"一直决定不了她往哪走"，经过改写的版本按要求走到位、按时切到特写。

### 2. H3-Base 吃的是"描述"，不是"指令"

官方改写结果的共同特征：
- 全是连续的英文描述，按播放顺序写，像有人看完成片后写下的说明；
- 没有一句规则、强调、禁令；
- 物理过程写全（"冲击让舰桥剧烈一震，舰长被带得向前踉跄半步，肩膀绷紧稳住身体"）；
- 后面的镜头复指前面的人（"the captain from Shot 1"）；
- 台词前写声线，台词后写闭嘴；
- 一段 2–4 个镜头，正文 350–500 词。

旧 skill 产出的提示词里，大量内容不是描述而是给人看的规则：`IMPORTANT —`、`FORBIDDEN`、`(flame: ON)` 状态标签、全大写运镜词和动词、`[Shot N · 1.5–2.8s]` 区间镜头头、`Line lands about 2.80–3.90s`、`Total runtime is exactly 15.08 seconds`、`Acting direction for the whole sequence:` 等。H3 的文本编码器是 Qwen3-VL-32B，能"读懂"这些话，但视频生成部分是在 Context-IR 文体上学会"文字 → 画面"的，规则式文字离它的训练分布很远，执行起来就不稳定。

**纠正一下我前面的说法**：之前说"skill 太长导致过载"不完全对。官方改写结果本身就有 400–600 词，你本地跑通的范例 5 也有近千词。问题不在总字数，在于**字数花在了什么上**：官方把字数花在少数几个事件的可见细节上；旧 skill 把大量字数花在规则、标签、重复强调上，同时一段里塞的事件和镜头太多。

### 3. 内容设计要绕开 H3 的弱项

各家评测一致的弱项：手和道具的精细交互、多人同时动作、接触和撞击、快速大幅动作、遮挡后重现、多镜头连续性；本地 768p 下远景人脸和小字会糊。物理问题的研究（PhyT2V，CVPR 2025）表明：先找出场景涉及的物理规律，再把它写进提示词，物理正确率能提高约 2.3 倍；也有机器人方向的研究报告，把动作分步拆解写进提示词能明显减少物理错误。

### 4. 一些硬规则

- **合法时长**：帧数必须满足 n % 17 == 5，5–15 秒之间只有 15 个合法时长，只有 8 秒是整数。填 10 秒实际出 10.125 秒，填 15 秒实际出 15.083 秒。
- **切点**：开源复刻项目的校验器要求每个镜头至少约 1.2 秒；本 skill 对话和文戏取 1.5 秒，快动作取 1.0 秒（第一轮出片后改的）。
- **符号**：结构部分混入弯引号、全角括号、全角逗号会改变分词，标记词会失效。
- **CFG**：开源权重是 CFG 蒸馏过的，Turbo LoRA 也是免引导蒸馏，CFG 保持 1.0。
- **步数**：挂 Turbo LoRA 时社区实测 6–8 步最好；LoRA 强度推荐 1.0。
- **中文台词**：社区测试建议每秒不超过 3.2–3.5 个字；一个镜头一个说话人是最可靠的对嘴办法。
- **A/B 陷阱**：H3 把文字和视频排在同一条序列里，提示词变长会让视频部分的位置编码整体后移。所以"加一句话变好了"可能是长度在起作用。

### 5. 真人短剧的通行流程

行业普遍做法是"先出图、再图生视频"：角色定妆照 → 每个镜头先用图像模型出首帧 → 图生视频（I2VA）→ 段与段用末帧接力。纯文生的人物每段都会重新长一遍，一致性最差。

## 二、新 skill 做了什么

1. **定位改成"替官方 Context-IR 干活"**：产出必须长得像官方改写结果。新增"可观察测试"：每句话都得是看得见或听得见的描述。
2. **默认格式全面对齐官方**：镜头头 `[Shot N] At MM:SS.mmm`、运镜用官方自然句、声音字段用连续段落、状态用陈述句、规则改成正向陈述。
3. **降低密度**：镜头数按官方分布（每段 2–4 镜为主），每镜至少 1.5 秒，一镜一个主动作。（第一轮出片后已改为按戏的类型定：快动作和多节拍文戏保留密切切镜，快动作每镜至少 1.0 秒，见 `tools/context_ir/analysis/RENDER_RESULTS_1.md`。）
4. **新增物理写法**：起因 → 用力 → 反应 → 落定；H3 做不好的事情清单和绕开办法。
5. **保留所有实测有效的东西**：电影感底座、活人感、防串词、画外音句式、台词预算、项目卡。
6. **新增合法时长表和校验脚本** `scripts/lint_prompt.py`：自动查规则词、标签、全角符号、切点、时长、台词字数、Ref2VA 标签。
7. **新增病症对照表**：出片后按"哪里乱"对症改。
8. **主文件从 769 行缩到约 150 行**，其余放进按需读取的参考文件。
9. **给了两组新旧写法 A/B 对照**（《纸引》EP1-06、《临期》段 04），用来在你本地验证新文体。

## 三、建议你接下来做的事

（2026-10-07 进度：第 1、2、5 项已经做完。两轮本地出片对比的结果见 `tools/context_ir/analysis/RENDER_RESULTS_1.md` 和 `RENDER_RESULTS_2.md`，A/B 表已回填，验证过的新文体范例在 `examples.md` 第 3 节。）

1. **先跑两组 A/B**（原文现在在 `tools/context_ir/old_versions/`、`skill_versions/`、`round2/`；`examples.md` 第 3 节改放验证过的 v2），每组至少 2 个种子，结果填进 A/B 表。这一步决定新文体是不是真的更好。
2. **用官方 Context-IR API 改写 3–5 段典型戏**当"标准答案"，和 skill 写的版本同种子对比。这是找出差距最快的办法。
3. **核对采样设置**：CFG 1.0、步数 6–8、Turbo LoRA 强度 1.0 对比你现在的 0.75。
4. **关键镜头改用首帧流程**（图像模型出首帧 → I2VA）。
5. 另外两个配套 skill（`h3-director-json-review`、`h3-action-prompt-design`）还按旧写法引用这个 skill，新文体验证通过后需要同步更新。
